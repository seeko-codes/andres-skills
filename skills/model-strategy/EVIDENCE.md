# Validating the model policy

This public edition preserves the local policy's routing rules without publishing
machine-specific model IDs, context limits, or claims about a provider's current lineup.
The tier labels in `SKILL.md` are assignments to validate, not benchmark rankings.

## Before changing the mapping

1. Inspect the active runner's available models and accepted effort settings.
2. Check current provider documentation for the exact IDs being considered. Do not infer
   availability or capability from another runner's configuration.
3. Compare candidates on representative work with known acceptance criteria. Include a
   bounded implementation, an ambiguous diagnosis, a consequential review, and an exact
   extraction task when those are part of the workload.
4. Record task success, escaped defects, and rework before comparing latency or usage.
   Change model and effort independently so the comparison identifies what helped.

## Boundaries of the policy

A reliable verifier can make a lower-tier model useful for bounded work. It does not
establish that the same model can judge requirements, notice a flawed brief, or review a
change whose failures are hard to detect. Treat those as separate evaluation tasks.

Independent context reduces shared assumptions, but a reviewer still needs enough
capability to find the relevant defects. More agents or more effort are not substitutes
for a demonstrated quality bar.

Question ordering and prediction checks are prompt procedures. They neither select a
stronger model nor change the runner's reasoning-effort setting.
